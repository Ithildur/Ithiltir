# Architecture

Ithiltir Dash is a single-instance application. The root entry point starts one HTTP process that wires the API, SPA, theme assets, install scripts, node asset downloads, and background services.

## Runtime Boundaries

| Component                  | Responsibility                                                                                                                            |
| -------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------- |
| `cmd/dash`                 | process entry, config loading, dependency wiring, migration, update, Redis checks, and shutdown                                           |
| HTTP server                | mounts `/api`, `/theme`, `/deploy`, and the SPA                                                                                           |
| PostgreSQL + TimescaleDB   | durable metrics history, traffic facts and materialization progress, node metadata, alert rules, encrypted notification configuration and outbox, and system settings |
| Redis                      | admin sessions; disposable frontend runtime/metadata snapshots, SMART/thermal fields, node catalog, and guest-visibility catalog          |
| process memory             | decrypted notification configuration, `--no-redis` admin sessions, node auth index, alert queue/latest snapshots/runtime, MTProto login state, and volatile Node updates |
| Dash home filesystem       | owner-only notification-configuration key (root-owned in managed Linux installs) and mutable installation/runtime state                  |
| Node                       | pushes metrics and static host data; receives update manifests                                                                            |
| Linux node service manager | systemd or OpenRC/supervise-daemon owns the foreground Node process; explicit `none` mode leaves process ownership to the operator        |
| Linux root-side caches     | systemd timers refresh SMART, connections, and LVM caches; Alpine/OpenRC uses BusyBox cron for SMART and LVM only                         |
| web UI                     | reads dashboard data and submits admin operations                                                                                         |

## HTTP Surface

| Prefix            | Role                                                    |
| ----------------- | ------------------------------------------------------- |
| `/api/auth`       | login, refresh, logout, session revoke                  |
| `/api/version`    | Dash version and bundled node version                   |
| `/api/front`      | dashboard reads                                         |
| `/api/metrics`    | metrics history and online-rate queries                 |
| `/api/statistics` | statistics access policy and traffic statistics queries |
| `/api/node`       | Node pushes and node identity reads                     |
| `/api/admin`      | admin writes                                            |
| `/theme`          | active theme CSS, theme manifest, and preview images    |
| `/deploy`         | install scripts and packaged node assets                |
| `/`               | SPA                                                     |

## Data Flow

1. Nodes submit metrics and static host data through `/api/node/*`.
2. Successful metrics responses can include an update manifest.
3. PostgreSQL + TimescaleDB store durable history, traffic facts, ordinary configuration, encrypted notification-channel configuration, and notification outbox rows.
4. Redis stores admin sessions and the disposable frontend cache in the default mode; `--no-redis` replaces both with process memory. Alert runtime and MTProto login handshakes always stay inside the single Dash process.
5. Background services evaluate alerts, deliver queued notifications, and aggregate traffic data.

Node IP is an observation from authenticated Node requests: Dash reads the first IP in `X-Forwarded-For` when that header is present, otherwise it falls back to `RemoteAddr`; invalid values are not used. This field is for display and operations, not an auth boundary.

## State And Retention

- Default startup needs PostgreSQL and Redis `6.2.0+`; Redis `8.2.3+` is recommended. Dash validates the actual connected server with `PING` and `INFO server`, so the configured Redis account must permit both commands. An unavailable, unidentifiable, or pre-6.2.0 server stops startup, while versions below 8.2.3 remain supported and produce a startup warning. Redis stores admin sessions and the disposable frontend cache, and individual Redis failures do not fall back to memory. With `--no-redis`, Redis connection and version checks are skipped and sessions plus the frontend cache are wired to process memory from startup.
- `app.timezone` is compiled during startup. Empty uses the local timezone; non-empty values must be valid IANA timezone names, otherwise config loading fails with the configured value in the error.
- Frontend cache v2 uses the `ithiltir:dash:` project namespace: `ithiltir:dash:front:v2:node:runtime:{id}`, `ithiltir:dash:front:v2:node:meta:{id}`, `ithiltir:dash:front:v2:node:smart:{id}`, `ithiltir:dash:front:v2:node:thermal:{id}`, `ithiltir:dash:front:v2:node:ids`, `ithiltir:dash:front:v2:node:catalog`, `ithiltir:dash:front:v2:guest:ids`, and `ithiltir:dash:front:v2:guest:catalog`. Legacy v1 and unnamespaced v2 cache keys are ignored without dual-write and are never deleted automatically at startup; a cold cache is rebuilt lazily. Admin sessions retain the compatibility prefix `auth:jwt:*` so existing sessions survive an upgrade; startup neither migrates nor deletes that prefix.
- PostgreSQL is authoritative for node metadata and current metrics; for the node projection, Redis or the `--no-redis` memory backend is only the frontend serving index. Runtime samples and PostgreSQL-derived metadata are stored separately and composed into the unchanged public `NodeView`. Ordinary accepted metric samples update only runtime/SMART/thermal and do not change the catalog projection generation. Runtime from an ID absent from the current catalog is retained as a sample, invalidates that catalog, and never adds membership; only a PostgreSQL projection rebuild decides membership and metadata. A full rebuild replaces metadata and catalogs but uses create-if-absent writes for runtime, so a concurrent newer sample cannot be overwritten and sustained metrics cannot starve rebuild publication. The node domain owns lifecycle serialization: global changes use its exclusive structural side, single-node projection changes use the shared side plus a node-local lock, and high-frequency runtime writes use only the node-local lock. Different nodes remain concurrent while no single-node projection change can overlap a global change. A separate generation gate conditionally publishes rebuilds and does not hold its mutex across database or cache I/O. The representative logical disk's path, filesystem type, and capacity are one last-known observation: a report without a usable path preserves the entire previous observation, while a report with a path replaces all three fields and stores unavailable type or capacity as unknown. Node name/order/tag changes and frontend-relevant static fields invalidate metadata only; guest visibility invalidates only the guest catalog; traffic settings, secrets, groups, hostname/IP/Node version, CPU vendor/frequency, disk total, RAID capability, and report interval do not write frontend Redis state. Bulk ordering and node membership changes invalidate the node catalog. PostgreSQL metadata transactions perform the required Redis invalidation before commit; Redis failure rolls back PostgreSQL, while a later PostgreSQL commit failure leaves only a cache miss. Node deletion invalidates catalogs before commit and removes runtime keys only after a successful commit.
- At the authenticated node ingest boundary, values written to PostgreSQL are decoded directly into the corresponding signed Go widths. JSON decoding enforces representability, semantic validation enforces non-negative counters and valid numeric domains, and persistence does not perform narrowing casts. Bounded protocol identifiers are length-checked in the existing report traversal, while hostnames, operating-system paths, mountpoints, and hardware descriptions use storage sized for normal system observations. The Node's ordinary positive JSON encoding is unchanged and remains compatible.
- Admin sessions are stored in Redis by default and survive Dash process restarts and in-place upgrades; under `--no-redis` they are process-memory state and expire on restart. Alert evaluation state and MTProto login handshakes are process-memory state in both modes and intentionally reset on restart. Open firing alerts are restored from PostgreSQL events; pending and cooldown phases are not restart-persistent. Metric commits queue the latest evaluation snapshot in memory, while rule/full reconciliation falls back to PostgreSQL current metrics and never reads the frontend Redis cache. Missing optional runtime fields preserve existing firing state, and a frontend cache miss cannot close an alert as recovered.
- The SPA root owns browser-bundle version coherence. While the document is visible, one root runtime checks the local `/api/version`; a changed Dash version reloads the document, regardless of the active page. Page-level update UI owns only update controls and presentation, and remote release availability never gates loading a locally installed frontend.
- Dash has one operator, one running instance, and one built-in post-install executor: `DASH_HOME/bin/dash update`. `install_dash_linux.sh` is a first-install-only entrypoint, while `update_dash_linux.sh` is a compatibility wrapper with no update logic. Dash and automatic-update services are controllers: they resolve a GitHub Releases target, persist an immutable plan containing the target version, expected current version, and expected installation revision under `DASH_HOME/runtime/dash-update/jobs/<job-id>`, then launch the hidden `dash update execute` command in a systemd transient unit. The executor acquires the root-owned cross-process lock before re-reading installed state and uses compare-and-swap semantics; a stale plan fails instead of selecting a new target or rolling the installation backward. Manual execution uses the same executor and lock. The admin controller remains systemd-only; the executor also supports explicit manual installations. Job origin, phase, status, failure code, recovery path, and log are persisted atomically; a separate `current` job symlink only selects what the admin API displays. A completed cutover transaction remains as recovery evidence until the terminal job status is durable, and status reconciliation can derive the terminal outcome from that transaction after an executor crash. Automatic notification delivery scans every unacknowledged terminal automatic job and uses its job ID as the durable outbox key.
- Packaged files live in immutable directories under `DASH_HOME/releases`; an atomic `current` symlink selects the active release, legacy flat paths remain compatibility aliases for the migration window, and mutable runtime/configuration paths remain at `DASH_HOME`. A Linux release-format-v1 archive must contain matching `release.env`, `bin/dash`, `dist/index.html`, all seven bundled node/runner assets for the five supported platform/architecture targets under `deploy`, `configs/config.example.yaml`, and the Linux install/update scripts. The manifest binds every bundled asset by SHA-256, and the candidate Dash binary must report matching Dash and bundled-node versions before the live process is stopped. Official frontend builds also require non-empty `dist/theme-bootstrap.js`; arbitrary custom frontend distributions are outside the release contract. Archives allow only regular files/directories under one root and are bounded to 1 GiB compressed, 4 GiB expanded, and 20,000 entries. Staging and legacy recovery assets are sibling directories on the installation filesystem. The executor preserves the installed systemd/manual runtime mode and whether the managed service was active. A restarted systemd service must remain `active/running` without increasing `NRestarts` for five seconds before the update can complete; failed stabilization restores `update.block` and stops the service for recovery. For a manually launched runtime, the executor stops only server-mode Dash command lines from the managed installation and does not terminate maintenance subcommands.
- `runtime/dash-update/transaction.env` is the durable cutover record. Before stopping a systemd-managed Dash, the executor installs a permanent service condition and creates `update.block`; a reboot or unexpected executor death therefore cannot start Dash in the pre-migration or partially migrated interval. Before migration begins, recovery restores the previous release and runtime state. Once migration begins, recovery always activates the candidate and completes forward; it never restores an old binary over a possibly newer schema. After migration succeeds, the block is removed before service start, while the transaction remains until start and cleanup succeed. Completion is first persisted as a terminal transaction, then as terminal job status, and only then is the transaction removed. If the executor dies between those writes, reconciliation restores the job status from the terminal transaction instead of inventing a failure. `dash update recover` resumes or rolls back the recorded transaction. Goose's `goose_db_version` remains the sole schema-version source of truth: `dash migrate` advances older schema and rejects newer schema, while normal startup requires an exact match. GitHub Releases metadata and assets are the update root of trust; compromise of the GitHub account, token, repository, workflow, or release permission is equivalent to compromise of the update source.
- The Linux node installer owns installation and forced reinstallation, not version upgrades. It stages and executes the downloaded binary before stopping systemd, OpenRC, and matching manual runtimes, then replaces the managed release, report configuration, service/collector assets, and atomically switches the `current` symlink. The runtime user owns the node data and release tree because the unprivileged Node self-update protocol creates and switches releases; root-owned service and collector assets remain outside that tree. Installer downloads follow at most five redirects, only to the original host, preserving the effective port on same-scheme hops and allowing only HTTP-to-HTTPS scheme changes. Node version upgrades and their recovery semantics belong to the separate node self-update path.
- The active theme ID is durable configuration, while theme resolution is disposable presentation state. A missing or invalid selected package is recorded as `missing` or `broken`, runtime serves the frontend's built-in default skin, and theme management remains available for repair or reselection. Database and theme-root access failures remain operational errors. Theme package format v1 is frozen and deprecated but remains compatible; it receives no new syntax or capabilities. Additional capabilities require a distinct format version. The fixed `/theme-bootstrap.js` asset uses `Cache-Control: no-store`; other static assets retain their own cache behavior.
- SMART, thermal, and full RAID details are runtime state. SMART cache freshness, helper availability, device health, full thermal sensor payloads, and full RAID array/member payloads are kept in current snapshots or hot caches rather than historical PostgreSQL metric rows. SMART temperature for confirmed physical disks is reduced into `disk_physical_metrics.temp_c` for per-device history; virtual disks and RAID devices are ignored. The same backend decision produces `disk.temperature_devices` for frontend history navigation. Thermal data is reduced into `cpu_temp_c` for server history, while full thermal details are split into a separate frontend field cache; runtime fields are composed into the frontend node JSON on read.
- TCP/UDP connection counts are persisted numeric metrics. They are written to `tcp_conn` and `udp_conn` and remain available to history queries as `conn.tcp` and `conn.udp`. On systemd Linux hosts, full host/netns connection counts come from the one-second root-side connections cache because the Node runs with low privileges; the installer compiles this helper locally when `cc`, `gcc`, or `clang` is available. OpenRC does not run this helper because BusyBox cron cannot preserve its one-second interval. If the cache is missing or stale, the helper cannot be compiled, or OpenRC is used, the Node uses its built-in connection counting, which may miss container connections.
- Linux PSI pressure metrics are fixed numeric time-series data. PSI `avg10`, `avg60`, `avg300`, and `total` values are stored as nullable columns on `server_metrics` and `server_current_metrics`; missing columns mean unavailable data, not zero pressure. Collection reason/status strings are ignored by dashboard persistence. PSI data feeds history, not alert evaluation.
- Alert evaluation reads the latest in-process ingest snapshot or the PostgreSQL current projection. Built-in offline, RAID, SMART health, and NVMe critical warning rules are derived from snapshot freshness and reported disk state.
- Alert events are not opened during the first minute after alert service startup.
- Metric commits place the latest node snapshot in a process-local alert dirty queue; control changes may enqueue only the node ID. Repeated marks for one node coalesce to the latest snapshot, while a mark received during evaluation schedules one more pass. The queue and runtime are not stored in Redis; startup reconciliation, PostgreSQL open events, and later metric reports restore evaluation after a process restart.
- Alert and Dash-update messages use one PostgreSQL notification outbox and one single-process delivery worker. Delivery has no runtime lease; a `sending` row left by an interrupted process is taken again on the next poll. The outbox persists whether an in-flight row is a blocked-channel probe, so crash recovery retains probe cadence and queue coalescing. After a remote send succeeds, the live worker retries only the local completion transaction and does not send that row again. During graceful shutdown it keeps a bounded 10-second completion window before allowing the process to exit. The boundary remains at-least-once across a process crash, or shutdown completion timeout, between remote acceptance and local commit because the remote protocols provide no shared idempotency receipt. Alert events and runtime state remain independent from delivery. When the first target load fails and no last-good snapshot exists, the transition is deferred for retry instead of being committed without an outbox; once a last-good snapshot exists, it remains usable during a refresh failure. Database-query or worker-local failures before a remote request is made only release the current item for another attempt; they neither consume remote-delivery attempts nor change channel health. Transient remote failures use 5–320 second exponential retries before entering `blocked`; deterministic configuration and endpoint rejection immediately block the channel's compatible pending/retry backlog so only one low-frequency probe is sent. Any failure by that blocked probe keeps the channel backlog coalesced and schedules the next 5/15/30/60-minute probe, subject to a bounded remote `Retry-After`; Telegram Bot `429` responses also read JSON `parameters.retry_after`. Disabled channels move unsent rows to `paused`. Corrupt payloads, deleted targets, and channel-type mismatches alone enter `discarded`. Saving, re-enabling, or successfully delivering through a channel wakes compatible work and resets its attempt budget. Channel configuration revisions prevent in-flight results for older configurations from changing current health or overwriting a concurrently replaced MTProto configuration. Delivery health is persisted on `notify_channels`; active queue counts and retry/probe times are derived from the outbox. Historical `failed_permanent` rows migrate to `blocked`, so endpoint recovery does not depend on opening the admin UI.
- The alert notification service owns default-target resolution and durable outbox insertion for system notifications. Callers receive either `queued` or the terminal `skipped_no_targets`; target-load or outbox failures remain retryable errors. The automatic-update controller owns only its job lifecycle: after either terminal enqueue result it writes `finish.handled`, while the legacy `finish.notified` marker remains accepted for cleanup compatibility.
- Notification channel configuration crosses one encryption boundary in the alert store. Dash encrypts the complete JSON document with AES-256-GCM and authenticates the channel ID and type as associated data; current logical rows retain ciphertext while the legacy `config` column contains only `{}`. The one installation key is the raw 32-byte `$DASH_HOME/configs/notify-config.key`, kept outside PostgreSQL with owner-only permissions. `dash migrate` creates it only when no ciphertext exists and converts every legacy row in one database transaction. Normal startup never creates or falls back to plaintext: it requires the key, the ciphertext-only storage invariant, and successful decryption of every channel, including soft-deleted rows. Database backups and this key must be stored separately; losing the key makes notification credentials unrecoverable. The migration does not physically erase former plaintext from MVCC dead tuples, table free space, WAL, replicas, backups, or storage snapshots.
- Alert control tasks remain `pending` while running or waiting for retry and are taken serially by the single-process worker; they have no runtime lease. Completed tasks are deleted. Failed rows remain as operational history but do not reserve the deduplication key, so a later reconciliation can enqueue the same logical repair again.
- Server, disk I/O, disk-usage, and physical-disk-temperature histories use one-hour raw chunks. Raw chunks remain uncompressed for one day, then stay losslessly compressed until `database.metrics_raw_retention_days` (default `8`, minimum `2`) removes them. The 15-minute aggregates retain 16 days and the one-hour aggregates retain 32 days; history queries use raw for `30m` through `24h`, 15-minute aggregates for `1w` and `15d`, and one-hour aggregates for `30d`. All history aggregates include the real-time raw tail; only `server_online_30m` remains completed-bucket-only.
- Raw NIC metrics continue to use one-day chunks, seven-day compression, and `database.retention_days` (default `45`). Five-minute traffic facts remain rowstore and use `database.traffic_retention_days`; no generic NIC rollup is introduced. Lite does not shorten these windows, so Billing rebuilds can use retained NIC samples. `traffic_5m` remains writable and rolling-retained, while monthly snapshots preserve historical 95th-percentile billing values.
- Capacity planning for the default lifecycle is about `24–26 GiB` of core time-series storage, `6–8 GiB RAM`, and `80–100 GiB SSD` at 100 nodes; at 500 nodes, about `120 GiB`, `16 GiB RAM`, and `250 GiB SSD/NVMe`.
- Traffic `lite` mode stores only per-interface monthly in/out totals, estimated peaks, coverage bounds, and per-row source progress in `traffic_month_usage`; it does not write 5-minute facts. One durable `usage` scan cursor owns only the global live head and restart catch-up; it does not replace each row's independent `last_collected_at` boundary or own local cycle repairs. Traffic `billing` keeps the same monthly accumulator as a shadow/continuity source and additionally maintains `traffic_5m` under its own `facts` cursor. Billing API totals and advanced statistics remain sourced consistently from `traffic_5m`. A Lite-to-Billing transition positions the Facts cursor at the most recent 30 minutes so current statistics recover first; older per-node history from the Lite interval stays out of the automatic catch-up path and is restored on demand by the Billing rebuild while raw NIC data remains retained.
- One background Service owns both explicit materializers. Each retains its own query, algorithm, cursor, and transaction. Every one-hour chunk commits derived rows and its cursor atomically; Usage and Facts failures therefore do not advance each other's progress. During each five-minute scheduler tick, each live materializer executes at most 12 one-hour chunks; node-local Usage repair has separate limits of 30 seconds and 120 six-hour chunks. The traffic write gate covers one chunk only. Usage catch-up is bounded by raw NIC retention, while Facts is bounded by the shorter raw NIC and fact retention. Materialization uses the current NIC projection and existing monthly accumulators as a small interface catalog, then loads the samples immediately before and after each interface window. Adjacent samples therefore remain fully accounted when they span an otherwise empty one-hour chunk. Facts idempotently replace overlapping buckets, while Usage uses each row's `last_collected_at` to avoid double counting and records one gap per affected billing cycle.
- Daily summaries, P95, coverage, and Billing monthly snapshots are derived from 5-minute traffic facts. The Billing-only per-node rebuild has one process-local state and no durable task or cursor. It uses the same write gate in 6-hour chunks and transactionally rewrites facts while invalidating overlapping monthly snapshots. A Dash restart cancels the task. Each chunk rechecks Billing mode, so switching to Lite prevents another facts chunk from starting.
- Billing cycles are node-owned and always stored explicitly. New nodes use `calendar_month`, day 1, and the application timezone by default; the global traffic row retains fixed cycle-shaped fields only for response compatibility and cannot change node cycles. Upgrading resolves each legacy `default` node to the global cycle that was effective before the migration, so existing cycle boundaries do not move. A node cycle change takes effect immediately, deletes only that node's affected monthly accumulators and snapshots, and merges one short-lived repair cursor into `traffic_usage_repairs`; the global live Usage cursor is not rewound. A node with an active repair is temporarily excluded from the live Usage scan and replays six-hour chunks from the earlier start of its old and new active cycles until it reaches the live head, while unrelated nodes continue updating. Catch-up remains bounded by raw NIC retention; insufficient coverage is represented by `covered_from` and the statistics completeness fields. Global direction remains a default that nodes may override. No cycle-rule history or pending configuration is stored.
- Traffic direction mode changes the selected billing view only; raw inbound and outbound counters remain stored separately.
- Metrics history is private by default. `history_guest_access_mode=by_node` exposes it only for guest-visible nodes.
- Traffic statistics guest access is controlled by traffic settings and still respects node visibility.

## Auth Boundaries

| Area                                                  | Auth                                                                                        |
| ----------------------------------------------------- | ------------------------------------------------------------------------------------------- |
| `/api/auth/login`                                     | admin password                                                                              |
| `/api/auth/refresh`, `/api/auth/logout`               | `SameSite=Strict` refresh cookie + `X-CSRF-Token`                                           |
| `/api/front/*`, `/api/metrics/*`, `/api/statistics/*` | optional bearer; anonymous requests are filtered by visibility settings                     |
| `/api/node/*`                                         | `X-Node-Secret`                                                                             |
| `/api/admin/*`                                        | `Authorization: Bearer <access_token>`                                                      |
| `/deploy/*` packaged assets                           | `X-Node-Secret` or a temporary legacy upgrade token; install script templates remain public |

## Frontend And Reverse Proxies

The frontend can run as a standalone dev server, but the runtime boundary stays same-origin. A dev proxy or production reverse proxy should forward `/api`, `/theme`, and `/deploy` to the backend while Dash serves the SPA at `/`. IP deployments may use HTTP; use HTTPS across untrusted networks because admin credentials and node secrets otherwise travel in plaintext. Do not point browser API requests directly at a cross-origin backend unless CORS, cookie, and CSRF policies are designed together.
